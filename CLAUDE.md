# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Владелец репозитория общается на таджикском (латиница/кириллица вперемешку с русским).
Отвечайте ему на таджикском. Код, комментарии, коммиты, тексты данных и документация —
на русском.

## Команды

```bash
npm install        # единственная зависимость — pg, нужна только при DATABASE_URL
npm run dev        # локальный сервер на http://localhost:3000 — API + страница документации
npm run generate   # пересобрать lib/dataset.json из описания каталога
npm run check      # проверка целостности данных, картинок и спецификации
npm run test:api   # сквозная проверка эндпоинтов: сам поднимает сервер и гасит его
```

Зависимости две: `jimp` (сжатие фотографий) и `pg` (нужен только при
`DATABASE_URL`). Обе подключаются `require`-ом внутри функций, поэтому холодный
старт от них не тяжелеет.

Тестового фреймворка нет, есть две обязательные перед коммитом проверки:
`npm run check` — данные и спецификация (падает, если нарушено любое правило из
раздела «Инварианты»), `npm run test:api` — 82 проверки по живым эндпоинтам:
чтение, регистрация с фотографией, маскирование, «Личные данные», владелец
записи, отзывы, CRUD, коды ошибок и обе страницы.
Обе должны быть зелёными.

Проверка ветки с PostgreSQL (сервер лежит в образе, но не запущен):

```bash
PGD=/var/tmp/pgdata
mkdir -p $PGD && chown postgres:postgres $PGD && chmod 700 $PGD
su postgres -c "/usr/lib/postgresql/16/bin/initdb -D $PGD -U karapuz --auth=trust"
su postgres -c "/usr/lib/postgresql/16/bin/pg_ctl -D $PGD -o '-p 5433 -k /var/tmp' -l $PGD/server.log start"
psql "postgresql://karapuz@localhost:5433/postgres" -c "create database karapuz;"
DATABASE_URL="postgresql://karapuz@localhost:5433/karapuz" npm run dev
```

Проверка страницы документации делается через Playwright, установленный глобально
(`/opt/node22/lib/node_modules/playwright`), браузер лежит в `/opt/pw-browsers`.
Запускать `playwright install` не нужно.

Локальный сервер держится в фоне; перед перезапуском убивайте старый, иначе новый
не займёт порт и вы будете тестировать устаревший код:

```bash
for p in $(pgrep -f 'node scripts/dev[-]server.js'); do kill "$p"; done
```

## Архитектура

### Одна функция на весь API

На бесплатном тарифе Vercel деплой ограничен **12 serverless-функциями**. Когда их
стало 14, деплой начал падать на шаге «Deploying outputs» уже после успешной сборки.
Поэтому весь API обслуживают две тонкие обёртки над общей точкой входа:

```
api/[...path].js  ─┐
api/route.js      ─┴→ lib/api-entry.js → lib/router.js → lib/handlers/*
```

`lib/api-entry.js` делает ещё три вещи, общие для всех эндпоинтов: ставит адрес
сервера для абсолютных ссылок, считает лимит частоты (`lib/rate-limit.js`) и
перехватывает исключения обработчиков. Наружу из 500 уходит только «Внутренняя
ошибка сервера» — стек пишется в лог. Заголовок `OPTIONS` обрабатывается там же
и лимит не тратит.

`lib/api-entry.js` достаёт путь тремя способами по очереди: параметр маршрута как
массив (catch-all), как строка (rewrite из `vercel.json`), и из самого `req.url`.
Так эндпоинты работают независимо от того, как хостинг передаёт параметры — на это
уже наступали, когда catch-all на проде отдавал 404.

`lib/router.js` разбирает путь. Порядок важен: служебные разделы (`products`,
`categories`, `subcategories`, `promotions`, `blog`, `images`) проверяются **до**
читаемых адресов каталога, иначе `/api/products` уйдёт в обработчик категории.

`scripts/dev-server.js` вызывает ту же `lib/api-entry.js` — маршрутизация одна на
локальную разработку и прод.

**Не добавляйте новые файлы в `/api`.** Новый эндпоинт — это новая ветка в
`lib/router.js` плюс обработчик в `lib/handlers/`. `npm run check` падает, если
функций в `/api` стало больше 12.

Служебные разделы перечислены в `RESERVED` в `lib/router.js`, а список
занятых slug'ов экспортируется оттуда же как `RESERVED_SLUGS` — `scripts/check.js`
берёт его, чтобы списки не разъезжались.

### Аккаунты — это тренажёр, а не защита

```
lib/config.js      настройки из окружения, все со значениями по умолчанию
lib/security.js    scrypt для паролей, JWT HS256, маскирование личных данных
lib/multipart.js   разбор multipart/form-data
lib/image.js       обрезка фото в квадрат 512×512 и сжатие (jimp)
lib/rate-limit.js  скользящее окно в памяти инстанса
lib/store/         index.js выбирает memory.js или postgres.js по DATABASE_URL
```

Владелец просил именно тренажёр для студентов, поэтому здесь сознательно
убраны вещи, которые обычно требуют:

- **Весь аккаунт — два запроса.** `POST /api/users` без `id` создаёт, с `id`
  сохраняет изменения; `DELETE /api/users/{id}` удаляет. Раздела
  `/api/auth` больше нет вообще: ни register, ни login. Владелец просил
  максимально просто — студент пишет одну функцию с `FormData` и
  переиспользует её на странице регистрации и на «Личных данных».
  `GET` у пользователей тоже убран, остался только файл фотографии
  `GET /api/users/{id}/avatar` — без него `<img src>` не заполнить.
  На странице Swagger из этих запросов показан **один** — `POST /api/users`
  с единственной формой `multipart/form-data`. `DELETE` и файл фотографии
  работают, но в спецификацию не попадают: владелец просил, чтобы студент
  видел ровно один запрос и одну форму.
- **Проверок нет.** Любая почта, любой пароль, пустые поля — всегда 201.
  Форма должна отправляться с первого раза. Не возвращайте сюда валидацию
  «как правильно», это осознанное решение.
- **Токен не требуется нигде.** `POST/PUT/PATCH/DELETE` работают без входа:
  `requireAdmin` и `requireUser` в `_helpers.js` при `adminWrites === false`
  возвращают гостя и никогда не отвечают 401. Строгий режим включается
  переменной `ADMIN_WRITES=true`.
- **Вместо прав — владелец записи.** При создании клиент может прислать
  `userId`; он ложится в `record.ownerId`, и `ownerBlocks` не даст изменить
  или удалить такую запись с другим `userId` (403). Записи из готового
  каталога владельца не имеют и открыты всем.

Что осталось строгим и трогать нельзя:

- `passwordHash` не покидает сервер ни в одном ответе. Пользователь наружу
  собирается только функцией `store.publicUser`.
- Роль назначает сервер: `role` из тела запроса не читается вообще.
- **Все личные поля маскируются**: `Ма*****`, `+9929001*****` (последние пять
  цифр), `saf*****@gmail.com`, `Душ*****`. Форма «Личные данные» заполняется
  этими же значениями и присылает их обратно — `security.isMasked` ловит такое
  и оставляет прежнее значение, иначе данные затирались бы звёздочками.
- Тип загруженной картинки определяется по первым байтам файла, а не по имени.

Аккаунтов держим `MAX_USERS` (50): после регистрации `store.enforceLimit()`
удаляет самые старые, кроме администратора. Каталог остаётся в памяти, в базе
живут только аккаунты, их фотографии и отозванные токены.

### Фотографии пользователей

`lib/image.js` принимает файл до 10 МБ, читает его через jimp, обрезает
`cover` в квадрат 512×512 и кодирует JPEG q80 — 27 МБ превращаются в ~80 КБ
за 3 секунды. Квадрат нужен именно для круглого аватара: круглая маска на
прямоугольном фото срезает половину лица.

Два подводных камня:

- **Vercel не пропускает запрос больше 4.5 МБ** — это лимит платформы, из кода
  его не обойти. В `MAX_AVATAR_BYTES` стоит 10 МБ, чтобы локально и на других
  хостингах работало полностью.
- **Swagger UI присылает поле `avatar` даже когда файл не выбран** — приходит
  пустая часть. Обработчик проверяет `data.length` и считает такое «файла нет»,
  иначе форма отвечала 400 на каждый запрос без фотографии.
- **Swagger UI подставляет `0` в незаполненное числовое поле.** Поэтому `id`
  считается указанным только если это положительное число, иначе POST принял бы
  ноль за «сохранить изменения пользователя 0» и отвечал 404. По той же причине
  `id` описан в схеме формы как строка, а не integer.

### Фильтры товаров — один набор на все списки

`applyProductFilters`, `applyProductSort` и `queryProducts` лежат в
`lib/handlers/_helpers.js`. Их используют `/api/products`, `/api/{category}`,
`/api/{category}/{subcategory}`, `/api/categories/{id}/products` и
`/api/subcategories/{id}`. Раньше каждый обработчик фильтровал по-своему, и
половина параметров работала не везде. Новый фильтр добавляйте туда, а не в
отдельный обработчик.

### Данные генерируются, а не пишутся руками

```
lib/tree.js      8 категорий → 39 подкатегорий: бренды, линейки, цены,
                 характеристики, цвета, материалы, фразы для описаний
lib/catalog.js   общие справочники: бренд→страна, авторы отзывов, пулы фраз
lib/copy.js      тексты: справка info у категорий, акции, описания подкатегорий
lib/blog-posts.json  24 статьи блога целиком
        ↓ scripts/generate-dataset.js (детерминированный, сид фиксирован)
lib/dataset.json     780 товаров, 8 категорий, 39 подкатегорий, 8 акций, 24 статьи
        ↓ lib/data.js
обработчики
```

`lib/dataset.json` — сгенерированный артефакт, он в репозитории, но править его
руками бессмысленно: следующий `npm run generate` перезапишет. Меняйте источник
и перегенерируйте. Генерация детерминированная — повторный запуск даёт побайтово
тот же файл.

### Конверт ответа

У **каждого** ответа одна и та же форма, как у остальных сервисов Softclub:

```js
{ data, errors, statusCode }              // + поля пагинации у списков
{ data: null, errors: ['текст'], statusCode: 404,
  error: { code: 'NOT_FOUND', message: 'текст', details: [] } }   // ошибка
```

Поле `error` добавлено к прежнему конверту, а не вместо него: `errors` и
`message` остались на месте, старый код читать ответы не разучился. Код ошибки
не зависит от языка сообщения — по нему клиенту удобно ветвиться.

Собирается в `jsonRes` (`lib/handlers/_helpers.js`), обработчики зовут `jsonData`
для объекта, `jsonErr` для ошибки, `jsonRes(res, 200, paginate(...))` для списка.

Правило, откуда оно взялось: фронтенд пишет `const { data } = await axios.get(url)`
и дальше `data.data.map(...)`. Поэтому **там, где эндпоинт про коллекцию, `data` —
сам массив**, а описание лежит рядом:

```js
GET /api/avtokresla/gruppa-1
data.data              // массив товаров, готов к .map()
data.subcategory       // описание подкатегории
data.category.info     // справка по категории
```

Так устроены `/api/{category}`, `/api/{category}/{subcategory}`,
`/api/categories/{id}`, `/api/subcategories/{id}`, `/api/products/{id}/reviews`.
Объект в `data` — только у одиночных записей (`/api/products/{id}`, `/api/blog/{id}`,
`/api/promotions/{id}`) и у ответов POST/PUT/DELETE.

Исключение из конверта одно: `/api/swagger.json` — это сама спецификация OpenAPI,
её оборачивать нельзя, иначе Swagger UI и Postman перестанут её понимать.

### Ссылки

Внутри данных ссылки хранятся относительными (`/api/images/…`, `/assets/…`,
`/api/kolyaski`), а наружу отдаются абсолютными: `jsonRes` прогоняет ответ через
`absolutize`, подставляя адрес сервера из заголовков запроса. Фронтенд живёт на
другом домене, относительный путь у него разрешился бы в его собственный адрес.

### Блог

`lib/blog-posts.json` — рукописный источник: у каждой статьи свои `description`,
`author` (имя, должность, slug, аватар), три тезиса `highlights`, цитата и текст.
`scripts/generate-dataset.js` дописывает к ним считаемое: даты в ISO,
`categorySlug`, счётчики и главное — `sections`. Это готовые блоки страницы в
нужном порядке (абзацы, иллюстрация после второго абзаца, цитата ближе к концу),
чтобы фронтенду не приходилось резать `content` самому.

Список `/api/blog` отдаёт всё, кроме `content` и `sections` — они приходят в
одной статье или по `?full=true`. Одна статья добавляет ещё `breadcrumbs`,
`prevPost`, `nextPost` и `related`.

Уникальность `description` и каждого тезиса проверяет `npm run check`: одинаковых
текстов от статьи к статье быть не должно.

### Отзывы

`id` отзыва сквозной по всему каталогу, а не по товару — иначе
`PATCH /api/reviews/{id}` не смог бы найти запись. Нумерация задаётся в
`makeReviews` в генераторе, у каждого отзыва есть `productId`. Отзыв, оставленный
через API, получает ещё `userId`: по нему проверяется, свой отзыв правят или чужой.

### Картинки

Внешних ссылок на фотостоки в данных нет ни одной — раньше были, и часть отдавала
404, в карточках висели битые изображения. Проверить их из среды разработки нельзя
(внешние домены закрыты), поэтому правило жёсткое: картинка либо лежит в репозитории,
либо рисуется API.

- `assets/products/{slug}.jpg` — студийная фотография, отдаётся статикой с CDN.
- `GET /api/images/{slug}.svg` — рисованная карточка (`lib/handlers/images.js`):
  фон в цвете категории, значок раздела, подпись. Префиксы: `cat-`, `sub-`, `post-`,
  `author-` — категория, подкатегория, статья и аватар автора (круг с инициалами).
- `GET /api/users/{id}/avatar` — загруженный аватар пользователя, отдаётся из
  хранилища двоичным ответом, а не в конверте.

Генератор сам решает, что подставить: есть файл в `assets/products` — ставит
фотографию, нет — рисованную карточку. Добавили новые файлы → `npm run generate`.

**Не читайте файлы картинок из обработчика через `fs`.** Трассировка сборки Vercel
не видит пути, собранные во время выполнения, такие файлы могут не попасть в бандл
функции — фотографии тогда молча подменятся заглушками, и это заметят только на проде.

### Две страницы

`index.html` — настоящий Swagger UI. Файлы лежат в `assets/swagger/` (скопированы
из пакета `swagger-ui-dist`, версия в `VERSION.txt`), а не подключаются с CDN:
внешние домены из среды разработки недоступны, да и на проде так надёжнее.
Сам пакет в зависимостях не нужен и удалён.

`docs.html` — прежняя страница каталога, теперь по адресу `/docs`.

### Что Swagger показывает, а что нет

Спецификацию собирает `lib/handlers/swagger.js` — не по списку методов, а по
самому каталогу:

- **Каталог перечислен поимённо.** На каждую категорию и подкатегорию свой
  путь со своим названием: `GET /api/detskaya-mebel` — «Детская мебель — вся
  категория», `GET /api/detskaya-mebel/krovatki` — «Детская мебель → Кроватки».
  Всего 47 готовых запросов, они строятся циклом по `categories`, поэтому новая
  категория появляется на странице сама. Общих адресов `/api/{category}` и
  `/api/{category}/{subcategory}` в спецификации нет: по ним не видно, какой
  раздел откроется, и все строки выглядели одинаково — владелец на это жаловался.
- **Фильтры описаны один раз** в `components.parameters` и подставляются
  ссылкой (`FILTERS`), иначе полсотни путей повторяли бы один и тот же список.
- **Теги по-русски**: Аккаунт, Каталог, Категории, Подкатегории, Товары,
  Отзывы, Акции, Блог, Картинки — это заголовки разделов страницы.
- **У категорий в спецификации только чтение.** `POST/PUT/PATCH/DELETE`
  на `/api/categories` работают, но не показаны: каталог студент читает,
  а пишет — в товарах, отзывах, акциях и блоге.

Скрытые пути перечислены в `HIDDEN` в `scripts/check.js` — иначе проверка
ругалась бы, что маршрут есть в роутере, но не описан в спецификации.

### Страница каталога

`docs.html` — один файл без сборки и зависимостей. Строится не из списка методов,
а вокруг каталога: блок на каждую категорию, внутри готовые GET-запросы (вся
категория плюс каждая подкатегория), у каждого своя ссылка, которая собирается на
глазах при изменении параметров. Пустые поля в ссылку не попадают. Отдельно — блоки
акций и блога и одна форма на POST/PUT/DELETE для всех разделов.

Данные для блоков страница берёт из `/api/categories`, а не из спецификации, поэтому
новая категория появляется на странице сама.

Сверху — раздел «Аккаунт»: две карточки, регистрация и «Личные данные».
Обе шлют один и тот же `POST /api/users` настоящим `multipart/form-data` через
`FormData` (свой `Content-Type` ставить нельзя, границы расставляет браузер) —
разница только в том, что вторая добавляет `id`. Выданный при регистрации `id`
подставляется во вторую форму сам. Внизу — аккордеон «Как пользоваться API»:
содержимое лежит в массиве `HELP`, по две строки на каждый пункт — русская
и английская.

Карточки разделов аккаунта и справки используют ту же разметку `.cat` +
`.cat-head` + `.cat-body`, что и каталог, поэтому общий обработчик клика
раскрывает их без отдельного кода.

При правке CSS помните: `display: grid` перебивает атрибут `hidden` — в файле есть
`[hidden] { display: none !important; }`, без него блоки не закрываются. Дети grid
и flex по умолчанию не сжимаются уже `min-content`, поэтому у контейнеров стоит
`minmax(0, 1fr)` и `min-width: 0` — иначе длинный JSON распирает карточку и на
телефоне контент обрезается.

## Инварианты, за которыми следит `npm run check`

- ровно 20 товаров в каждой подкатегории;
- статей блога не меньше 24, у каждой текст от 600 символов, две иллюстрации,
  цитата и теги;
- ни одного повторяющегося текста: описания категорий, справки info, тексты
  и заголовки акций, описания подкатегорий, тексты и цитаты статей;
- ни одной внешней ссылки на картинку; каждая ссылка на фотографию ведёт к файлу,
  который реально лежит в репозитории;
- slug категории не перекрывает служебные пути `/api/...`;
- каждый путь спецификации разбирается роутером;
- каждая категория и подкатегория перечислена в спецификации отдельным путём;
- функций в `/api` не больше 12;
- id отзывов сквозные и совпадают с `productId` своего товара;
- у каждой статьи есть непустое уникальное `description`, автор с аватаром,
  три тезиса и блоки `sections` с иллюстрацией и цитатой;
- есть `.env.example`, а `.env` перечислен в `.gitignore`.

Чего `check.js` не ловит и о чём надо помнить: `npm run test:api` проверяет
маскирование, лимит аккаунтов, владельца записи и обе страницы — гоняйте его
вместе с `check`.

## Деплой

Vercel, ветка `main`, без фреймворка. Статика раздаётся из корня репозитория,
`/public` создавать нельзя — тогда Vercel начнёт раздавать только его, и `index.html`
из корня перестанет открываться.

CORS для `/api` ставит код (`setCors` в `lib/handlers/_helpers.js`), а не
`vercel.json`: он умеет работать со списком `ALLOWED_ORIGINS`, а статический
заголовок в конфиге дублировал бы `Access-Control-Allow-Origin` и ломал бы
браузерную проверку. В `vercel.json` для `/api` остались только `nosniff`
и `Referrer-Policy`.

`engines.node` закреплён на `22.x`. Диапазоны вроде `>=18` Vercel принимает, но
печатает предупреждение на каждую функцию.

Работа ведётся в отдельной ветке `claude/...`, но владелец просит пушить и в
`main` — его Vercel собирает именно оттуда. После пуша в `main` подтягивайте
ветку к нему, чтобы они не расходились.

`DATABASE_URL` — по желанию: без неё регистрации живут до перезапуска функции,
с ней переживают деплой. `JWT_SECRET` теперь не критичен: токен обязателен
только в режиме `ADMIN_WRITES=true`.

Рерайты в `vercel.json`: `/` и `/swagger` → `index.html` (Swagger UI),
`/docs` → `docs.html`. Локальный сервер повторяет это же — иначе страницы
разъедутся между разработкой и продом.

Домен `swagger-wheat.vercel.app` из среды разработки недоступен (политика сети
закрывает внешние домены). Проверить деплой самостоятельно нельзя — просите
владельца открыть адрес или прислать лог сборки.

## Текущее состояние картинок

120 товаров из 780 уже имеют студийные фотографии (акции целиком, а также кроватки,
колыбели и люльки). Остальные 660 показывают рисованную карточку.

Фотографии генерирует сторонний бот по промту; готовые он присылает архивами или
коммитит в ветку. Порядок приёмки: взять из архива/ветки **только** `assets/products/*.jpg`
(бот кладёт рядом служебные папки на десятки мегабайт — их в `main` не переносим),
положить файлы в `assets/products/`, выполнить `npm run generate`, затем
`npm run check` и коммит. Имена файлов совпадают с `slug` товара, поэтому ссылки
переключаются без правок в коде.
